Architecture / WebAssembly

【考察】なぜAIエージェントにChromiumは重すぎるのか？ ――Cloudflare KitesurfのRust×Wasm構成と、クライアント完結型設計の共通点

2026年11月14日 著者: O-ya 読了目安: 約8分

自律型AIエージェントにWebページを巡回させ、情報を収集させ、フォームを入力させる。そうしたワークフローを実運用に乗せようとしたとき、開発者の前に立ちはだかる最大の壁は何でしょうか。LLMの推論コストではありません。「裏で起動するヘッドレスブラウザの重さ」です。

PuppeteerやPlaywrightをDockerコンテナに詰め込み、エージェント1回のリクエストごとにChromeを立ち上げる構成を組むと、あっという間にメモリが枯渇します。1インスタンスあたり500MBから1GB超のRAMを消費し、起動には2〜5秒のコールドスタートを要する。数十、数百のタスクを同時に捌こうとすれば、インフラ費用の大半がブラウザコンテナの維持費に消えていきます。

2026年11月、Cloudflareがオープンソース公開した「Kitesurf（cloudflare/kitesurf）」は、この不条理に対する極めて明快な回答でした。Chromiumを完全に捨て、RustとWebAssemblyだけでヘッドレスブラウザエンジンを再構築したのです。

このアプローチは、私がこれまで取り組んできた個人開発――Typst Wasmによるブラウザ内PDF組版、Web Audioによる再エンコードなしの音声分割、極小SLM（0.09B）のCPU完結推論――と根底の思想が完全に一致しています。なぜいま「脱Chromium」「脱重厚コンテナ」が必然となっているのか、エンジニアの視点から整理します。

1. 人間向けブラウザと、AIエージェント向けブラウザの断絶

私たちが普段使っているGoogle ChromeやSafariは、人間の感覚器官（目と指）に合わせて究極まで最適化された怪物ソフトウェアです。

  • 1秒間に60フレーム（あるいは120フレーム）途切れなく描画するGPUアクセラレーション
  • 滑らかなスクロール物理演算やアニメーション補間
  • タブごとの完全なマルチプロセス分離とサンドボックス保護
  • 膨大なWeb拡張機能やメディアコーデックのフルサポート

しかし、AIエージェントは画面を見て感動したり、滑らかなスクロールを味わったりしません。

エージェントが欲しいのは、「HTMLをパースしてDOMツリーを構築し、CSSを当ててレイアウト上の相対位置を把握し、必要なJavaScriptを実行して、目的の要素のアクセシビリティツリーやテキストを抽出すること」だけです。たまに画像認識用としてスクリーンショットを撮ることはあっても、リアルタイムに60fpsでGPU合成を行い続ける必要性はどこにもありません。

にもかかわらず、これまでの私たちは「人間向けの巨大なChromiumバイナリ」を丸ごとコンテナに載せ、仮想ディスプレイ（Xvfb等）経由でエージェントに操作させてきました。これが無駄でなくて何でしょうか。

エージェントが必要とするブラウザ機能の現実

・必須：DOM解析、CSSカスケーディング/ボックス配置、最小限のJS実行、要素の座標計算、スナップショット生成
・不要：GPUコンポジット、動画ハードウェアデコード、滑らかなアニメーション、拡張機能API、ブラウザプロファイル管理

2. Cloudflare Kitesurfのアーキテクチャ：RustモジュールをWasmに束ねる

Kitesurfの構造は非常に合理的です。ゼロから巨大ブラウザを書いたのではなく、Rustエコシステムにすでに存在する成熟したコンポーネントを厳選して組み合わせ、それをWebAssemblyにコンパイルしてCloudflare Workers上で動かしています。

+-------------------------------------------------------------+
|                 Cloudflare Kitesurf Architecture             |
|                                                             |
|   +-----------------------------------------------------+   |
|   |         CDP Interface (Chrome DevTools Protocol)    |   |
|   +-----------------------------------------------------+   |
|                              |                              |
|   +--------------------+     |     +--------------------+   |
|   |    Blitz Engine    | <---+---> |   Stylo Engine     |   |
|   | (DOM Parser & Box) |           | (Servo/Firefox CSS)|   |
|   +--------------------+           +--------------------+   |
|              |                               |              |
|   +--------------------+           +--------------------+   |
|   |  Boa JavaScript VM |           | Linebender 2D / Vello|
|   |   (Pure Rust JS)   |           | (Vector Graphics)  |   |
|   +--------------------+           +--------------------+   |
|                                                             |
|   Target: wasm32-unknown-unknown / Edge Worker Sandbox      |
+-------------------------------------------------------------+
  • Blitz：Dioxusチームが開発する軽量なHTML/DOMパースおよびボックスレイアウトエンジン。Taffyを利用してFlexbox/Gridを計算。
  • Stylo：Firefox/Servoから切り出された世界最速峰の並列CSSスタイルエンジン。
  • Boa：Pure Rustで書かれた組込み指向のJavaScriptエンジン。V8のような巨大なJITコンパイラを持たず、ステートレスに動く。
  • Linebender / Vello：フォント描画や2Dグラフィックスを正確にベクター計算するライブラリ群。

これらを束ねた結果、「ステートレスでメモリ数MB、コールドスタート数ミリ秒、CDP（Chrome DevTools Protocol）を喋れるブラウザ環境」が手に入ります。Cloudflare Workersのような「メモリ制限128MB・実行時間数ミリ秒」の極小エッジワーカー上で、数千台の仮想ブラウザを並列起動できる理由がここにあります。

3. クライアント完結型・エッジ完結型の共通定理

この「重厚な既存コンテナを疑い、Rust×WebAssemblyで単一責任のサンドボックスに落とし込む」という思想は、個人開発のプロダクト設計と完全に地続きです。

事例1：Typst WasmでLaTeXコンテナを撲滅した話（Markdown TeX Viewer）

かつてブラウザ上で美しい数式文書やPDFを生成しようとすると、サーバー側に数GBのTeX Live環境を立ち上げ、ユーザーの入力をPOSTしてコンパイル結果を返す構成が一般的でした。しかし、これではサーバーのスケールコストがかさみ、ネットワーク遅延でプレビューがもたつきます。

Rust製の新世代組版エンジン「Typst」をWebAssemblyへビルドしてブラウザに載せたことで、サーバー通信を完全に撤廃できました。ローカルのJavaScriptスレッドから数万行のマークアップを流し込むだけで、瞬時にベクターPDFがブラウザ内部で組み上がります。

事例2：ffmpegコンテナを介さない「無変換フレームコピー」（Symple Audio Splitter）

音声ファイルの分割・トリミングも同様です。多くのWebサービスはユーザーのギガ級音源をサーバーへアップロードさせ、ffmpegで再エンコードしてダウンロードさせます。

しかし、MP4/AACのコンテナ構造（moov/stbl/stszボックス）をブラウザのバイナリパーサーで読み解き、AACパケットやMP3フレームをヘッダごとそのまま切り出せば、再エンコードのCPU負荷はゼロになります。30分の音源を10分割するのに21秒待たされていた処理が、0.23秒で完了する世界に変わるのです。

事例3：0.09B極小モデルによるブラウザ完結型言語処理（ZeroConvert-IME）

「LLMを動かすには数十GBのVRAMと巨大なGPUサーバーが必要だ」という固定観念も、特定タスクに絞れば崩れ去ります。日本語の仮名漢字変換やタイポ補正という単一責任に特化させれば、モデルサイズは18.7 MiB（0.09B）まで圧縮可能です。

これをWebAssemblyやローカルプロセスで動かせば、GPUのないオフィスPC（VRAM 0MB）でもメモリ35MB、打鍵レイテンシ8.4msで推論が完了します。機密データを外部APIに一切送らない完全なプライバシー保護と、ゼロインフラ運用が同時に成立します。

4. 「コンテナを立てるな、Wasmに落とせ」の時代へ

クラウドコンピューティングの歴史は、「ハードウェアの仮想化（VM）」から「OSの仮想化（コンテナ）」へと軽量化を進めてきました。そして今、AIエージェントとエッジコンピューティングの爆発によって、コンテナのオーバーヘッドすら許容できないフェーズに突入しています。

Linuxカーネルやファイルシステム全体をエミュレートするコンテナは、多機能ですが重すぎます。これからのエージェントインフラやクライアントサイド開発に必要なのは、「単一の目的だけを果たす、メモリ安全で隔離された、ミリ秒で起動するサンドボックス」です。

KitesurfがChromiumを解体してRust×Wasmに再構築したように、あらゆる重厚な処理は今後、エッジやブラウザの軽量Wasmランタイムへと溶け出していきます。

  • 重いブラウザを回すのではなく、エージェント用の軽量パーサーを回す。
  • 巨大なサーバーでレンダリングするのではなく、クライアントのWasmで描画する。
  • クラウドの巨大LLMに頼るのではなく、手元の極小SLMで即座に判定する。

この設計規律を意識し続けることこそが、爆発する計算コストから自由になり、本当の意味でスケールする個人開発プロダクトを生み出す鍵になると確信しています。
