【考察】「Don't Sleep, Keep Watch」の知覚・行動ギャップ解消と、1打鍵5〜7msで動くZeroConvert-IME v0.9.0の同じ設計課題

1打鍵5〜7ms台で追従する極小AI日本語IME（Windows / Android）
トップで見る ↗ GitHub

AIが推論しているあいだに現実の画面や入力状態が先に進んでしまうと、モデル単体の精度がどれだけ高くても、返ってきた結果はその瞬間に古いものになります。

Hugging Face Daily Papersで注目を集めた論文『Don't Sleep, Keep Watch: Proactive Perception for Computer-Use Agents』（arXiv:2611.28947）は、まさにこの時間差を真正面から扱っています。巨大なVLMに画面操作を任せる際、モデルを賢くするのではなく、わずか0.8Bの軽量監視モデルを横に並べて古い行動を止める仕組みを提案しました。

この構造は、私が開発しているローカルAI日本語IMEのZeroConvert-IME v0.9.0で追いかけた設計課題とそのまま重なります。公開済みベンチマークの数値とあわせて、動的環境における応答速度と状態無効化の共通点を整理します。実装の詳細や学習レシピは（内部）に留め、ここでは公開されている性能結果と挙動のみを扱います。

1. NightWatchが突いた「知覚と行動のギャップ」

GUIを操作するVLMエージェントは、ある瞬間のスクリーンショットを受け取って長い推論を走らせ、数秒後にクリックや入力を返します。ところが動的なWebページやアプリでは、モデルが考えているあいだにロードが完了したり、ポップアップが閉じたり、ボタンの位置がずれたりします。

NightWatchの著者らはこのズレをperception-action gapと呼び、既存のVLM本体の重みやプロンプトを一切いじらずに外付けの軽量モデルNightWatch-0.8Bを常時ストリーム監視へ置く解決策を取りました。役割は3つに絞られています。

  • Interrupt：監視中に画面が予期せず変わったら、実行中の重い推論を途中で止める。
  • Void：推論が終わる直前に前提が崩れていた場合、発行予定だった古い操作を破棄する。
  • Wake：読み込みやアニメーションが落ち着いた瞬間を検知し、次の判断を即座に起こす。
NightWatch（arXiv:2611.28947）の主なベンチマーク結果

OSWorld-Verifiedではタスク成功率を維持・微増させたまま、非推論の壁時間を 33%削減、無駄な待ち時間を 53%削減 しました。動的なWeb操作を測るDynaCU-Benchでは、大型VLM単体の 39.5% → 44.2% へ成功率が伸びています。しかもこの0.8Bの監視モデルは、受動的な監視手法や30倍以上大きなSystem-1判定モデルを上回る結果を出しました。

要点は明確です。遅い推論をそのまま通すと、精度の低さではなく「世界の進行速度に負けた鮮度落ち」で失敗します。だから軽い監視役が前段に立ち、古い推論結果を容赦なく無効化できる構造が効きます。

2. 日本語IMEは毎秒何十回も起きる「動的環境」

人間がキーボードを打つ環境も、VLMにとってのGUIと同じく絶えず状態が変わる動的環境です。しかもGUI操作が数秒単位のやり取りなのに対し、タイピングは1打鍵あたり数十ミリ秒から百ミリ秒間隔で状態が書き換わります。

もし1回のAI変換やタイポ補正に50msや100msかかっていれば、結果を返す頃にはユーザーの指はすでに次の文字を打っています。変換候補のちらつきや、直前の誤字を直したつもりが次の文字と衝突して崩れる現象は、まさにIME版perception-action gapと言えます。

ZeroConvert-IME v0.9.0では、この問題に対して「1打鍵あたりの処理をディスプレイの更新周期より速くすること」と「文脈が進んだときに過去の判断を安全に撤回できること」の2点からアプローチしました。

3. 速さだけでなく「撤回と保留」で鮮度落ちを潰す

v0.9.0で特に手応えがあったのは、処理時間を削っただけでは解決しない境界を、挙動側の安全装置で塞いだ点です。

タイポ補正の短縮と、後続文脈での自動取り消し

入力中のタイポ補正は、Windows CPUの編集中シーケンス平均で 35.04 ms → 14.47 ms（約59%短縮）まで縮み、220msを超える遅延スパイクも1回から 0回 に抑えました。450問の合計壁時間も35.25秒から25.06秒へ落ちています。

ただ、入力途中の短い読みだけで補正を確定させてしまうと、続きの文字が打たれた瞬間に別の単語だったと判明するケースが出ます。そこでv0.9.0では、文脈が伸びた段階で「元の入力のほうが正しかった」と分かれば補正を自動で取り消し、別の候補が自然なら追従して再調整する挙動を入れました。納得いかないときはEscキーで生の入力へ戻せます。

自動確定の3段階化と誤確定ゼロ

先読みやライブ変換でEnter操作を減らす自動確定も、急ぎすぎれば誤確定になります。228件の長文評価でNano v4.2（18.7 MiB）の「早め」モードを測ったところ、自動確定が発動した文の割合は 55.3% → 83.3%、自動確定された読みの割合は 35.9% → 54.4% まで増えましたが、最終正解との誤確定は 0件（0.0%） を保っています。万が一確定した直後に言い回しを変えたくなっても、直後のBackspaceで未確定状態へ戻せます。

4. 2026年11月の開発トレンドに共通する「遅延と境界の制御」

この視点はAIエージェントやIMEに限った話ではありません。最近のGitHub Trendingで話題になったCloudflareやOxc周辺のRust製TypeScriptコンパイラ移植プロジェクト tsrs でも、GoではなくRustを選んだ理由としてWebAssemblyにガベージコレクタを抱え込ませずにブラウザやエッジで遅延なく動かす点が挙げられていました。また、数日前に取り上げたデスクトップ操作CLIの agent-desktop が画面変化を STALE_REF エラーで止める設計も、古い状態のまま手を動かさないための境界です。

巨大なモデルやリッチなランタイムをそのまま動かす時代から、軽量な監視やネイティブ実装でループを極限まで短くし、前提が崩れた出力は即座に無効化する時代へ移っています。モデルのパラメータを増やす前に、知覚から行動までの時間差をどれだけ潰せるか。NightWatchの0.8BとZeroConvert-IMEの18.7 MiBは、規模こそ違えど同じ現実解に辿り着いています。

まとめ

  • NightWatch（arXiv:2611.28947）は、0.8Bの常時監視モデルで古い推論や行動をInterrupt / Void / Wakeすることで、巨大VLMの壁時間を33%・無駄時間を53%削減した。
  • ZeroConvert-IME v0.9.0は、1打鍵5.31〜6.60 msのライブ応答と14.47 msのタイポ補正により、人間の打鍵速度の内側に推論を収めている。
  • 速度に加えて「追従再調整・自動取り消し」「誤確定ゼロの3段階自動確定」「Esc / Backspace復元」を組み合わせることで、動的入力における鮮度落ちを防いでいる。

When an environment changes faster than an AI model finishes thinking, even a highly capable model produces stale, wrong actions. The Hugging Face Daily Papers highlight "Don't Sleep, Keep Watch: Proactive Perception for Computer-Use Agents" (arXiv:2611.28947) tackles this perception-action gap by pairing a large VLM with a lightweight 0.8B System-1 watcher (NightWatch-0.8B) that interrupts stale reasoning, voids obsolete actions, and wakes the agent when UI state settles—cutting non-reasoning wall-clock time by 33% and wasted time by 53% on OSWorld-Verified, while boosting DynaCU-Bench success from 39.5% to 44.2%.

Live Japanese typing is an even tighter dynamic loop. ZeroConvert-IME v0.9.0 addresses the same perception-action gap through sub-frame local inference (5.31–6.60 ms per keystroke on Windows CPU, 32.92 ms on Snapdragon 8 Elite Android) and live-edit typo correction (35.04 ms down to 14.47 ms) backed by context-aware refinement, auto-revert, Esc raw restore, and 3-level auto-commit with zero miscommits on 228 long-form cases.
