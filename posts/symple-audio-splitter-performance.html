Web Audio / Performance

【開発記】書き出しを 72 倍速くした音声分割 PWA ― 再エンコードしない分割と、表示範囲だけの波形生成 【DevLog】Making a Browser Audio Splitter 72× Faster: No-Reencode Splitting and View-Scoped Waveforms

2026.11.10 著者: g0083 (O-ya tech) 関連: Symple Audio Splitter

mp3 / m4a をブラウザだけで分割する PWA「Symple Audio Splitter」を作りました。ファイルはサーバーに送らず、分割も書き出しも端末内で完結します。

最初の実装は素直でした。読み込み時に全部 PCM にデコードし、波形ピークを全編ぶん計算し、書き出すときは毎回 AAC / MP3 にエンコードし直す。機能は正しく動きますが、30 分の m4a を 10 分割すると全体で 21.5 秒かかり、そのうち 16.9 秒が書き出しでした。

この記事は、そこから書き出しを 16.9 秒 → 0.23 秒（約 72 倍）、体感を「待たされる」から「押した瞬間に終わる」へ変えるまでにやったことの記録です。速くするために機能を削るのではなく、やらなくていい処理をやめたのが主旨です。

波形上のダブルクリックで分割線を追加、ドラッグで移動。プレビュー再生は元ファイルをそのまま <audio> に渡している。

1. まず測る — ステージごとの内訳を出す

高速化で最初にやるべきは、体感ではなく内訳の計測です。このプロジェクトでは bench/ に Chrome を DevTools Protocol で操作する計測環境を置き、デコード / 波形ピーク / 書き出し / 合計を分けて記録しました。

node bench/make-fixtures.mjs          # テスト音源を生成 (ffmpeg が必要)
node bench/run.mjs --label before --format m4a --bitrate original --splits 9 --repeat 3

30 分ステレオ (44.1kHz) を 10 分割したときの初期実装はこうでした。

工程 時間 支配要因
デコード 4243 ms 全編 PCM 化
波形ピーク 438 ms 全編を走査
書き出し 16863 ms 10 セグメントを毎回 AAC エンコード
合計 21544 ms

書き出しが全体の 78% を占めています。ここを削るのが最短です。同時に、デコードと波形ピークは「書き出しのために必要」と思い込んでいただけで、実は再エンコードしないなら不要だという構造的な問題も見えてきました。

2. 読み込み: コンテナ解析だけで UI を出す

音声ファイルの長さ・サンプルレート・チャンネル数・ビットレートは、PCM にデコードしなくてもコンテナのメタデータから分かります。そこで decodeAudioData を待たず、数ミリ秒のヘッダ解析だけで画面を出すようにしました。

形式 読む場所 取り出す値
m4a moov > trak > mdia > mdhd / stsd 長さ、タイムスケール、チャンネル数、サンプルレート
mp3 フレームヘッダの連鎖 フレーム数、サンプルレート、平均ビットレート、チャンネルモード
wav fmt / data チャンク フォーマットタグ、ビット深度、データ長

再生は AudioBuffer ではなく <audio> + Blob URL にしました。ブラウザのメディアスタックがそのままデコードしてくれるので、アプリ側で PCM を持つ必要がありません。結果として、30 分 m4a は操作可能まで 0.08 秒（従来は 8〜10 秒ブロック）になりました。

PCM デコードは「必要になった瞬間」だけ

PCM を使うのは mp3 / m4a へ再エンコードする経路だけです。既定の「元のまま」では一度も呼ばれません。AudioSource.loadPcm() を遅延評価の Promise にしたので、同じファイルに対しては最初の 1 回だけデコードされます。

3. 波形: 全編ではなく「見えている範囲」だけ作る

波形ピークは 1 ピクセルあたり 1 個あれば十分です。全体表示なら 1 ピークが数万サンプルを担当し、拡大すれば数百サンプルになります。つまり全編を同じ精度で計算するのは無駄です。

そこで波形は表示範囲と解像度から必要なピーク間隔（256〜65536 サンプル、2 の冪）を決め、範囲の先頭フレームへシークしてデコードする方式に変えました。ズームやパンで足りない範囲だけを追加要求します。

// src/workers/peaks.worker.ts (抜粋)
// 1 ピークが複数フレームにまたがる場合はフレームを間引く
const frameSamples = /* 1 フレームのサンプル数 */;
const step = Math.max(1, Math.floor(bucket / Math.max(1, frameSamples)));
// 間引き時は 1 フレームのピークを step フレーム分へ引き伸ばす
const spanSamples = step > 1 ? step * frameSamples : 0;

デコードには WebCodecs の AudioDecoder を使い、100ms ごとに range-partial を返して波形を左から順に埋めます。30 分 m4a の全体波形は0.36 秒で描画され、拡大時は表示範囲の先頭からデコードするので一瞬で終わります。拡大時のピークは decodeAudioData の結果と一致すること（最大誤差 0.0007）も確認しました。

Worker には File を渡す

解析対象のバイト列はメインスレッドから送らず、File をそのまま Worker に渡して Worker 側で arrayBuffer() します。41MB のバイト列を構造化クローンで複製すると、コピーだけでメインスレッドが数百ミリ秒止まるためです。

また Worker は波形用と RMS 用で 2 つに分けました。1 つに相乗りさせると、全編 RMS の計算中にズーム操作が待たされてしまいます。無音検出用の 10ms RMS はバックグラウンドで作り、分割や書き出しを始めたら terminate() で止めます。

4. 書き出し: 再エンコードを捨てる

ここが最大の改善です。音声分割は「入力と同じ形式で、品質も元のまま」が既定なら、音声データを一切作り直さずに切れ目をコピーするだけで成立します。

経路 方式 10 分割の書き出し
m4a → m4a（元のまま） AAC サンプルをコピーして mp4-muxer で再構成 47 ms
mp3 → mp3（元のまま） フレーム境界でバイト列を切り出す 28 ms
wav → wav（元のまま） PCM をフレーム境界でコピー（ビット深度も維持） 67 ms
m4a（ビットレート指定） WebCodecs AAC + mp4-muxer 1568 ms
mp3（ビットレート指定） lamejs（Web Worker） 10653 ms

3 分ステレオ 44.1kHz・10 分割・中央値。再エンコード経路はデコードを含まない書き出し時間。wav は 24bit PCM（47.6MB）で計測。

m4a: サンプルインデックスを作って切り出す

mp4 の stbl にはサンプルごとの位置と長さが入っています。stco（チャンクオフセット）、stsc（チャンク内のサンプル数）、stsz（サンプルサイズ）を展開すれば、各 AAC サンプルのバイトオフセットが求まります。あとは範囲に含まれるサンプルを addAudioChunkRaw() でそのまま muxer に渡すだけです。

// src/audio/m4acopy.ts (抜粋)
const { from, to } = sampleRange(index, startSec, endSec);
const muxer = new Muxer({
  target,
  fastStart: 'in-memory',
  audio: { codec: 'aac', numberOfChannels: index.channels, sampleRate: index.sampleRate },
  firstTimestampBehavior: 'offset',
});

for (let i = from; i < to; i++) {
  const offset = index.offsets[i];
  const size = index.sizes[i];
  muxer.addAudioChunkRaw(bytes.subarray(offset, offset + size), 'key', timestamp, duration, meta);
  timestamp += duration;
}

エンコードが無いので、10 分割でも 47ms。30 分のファイルでも 232ms です。分割点はサンプル境界に丸め、隣接区間で同じ境界を共有するようにしたので、サンプルの重複も欠落もありません。

mp3: フレームを数えてバイト列を切る

mp3 はフレーム長がヘッダから決まります。全フレームのオフセットを一度インデックス化しておけば、指定時間に最も近いフレーム境界を求めて subarray() するだけです。7061ms → 28ms になりました。

wav: PCM をそのまま運ぶ

wav は blockAlign の倍数で切り、44 バイトのヘッダを付け直すだけです。元が 24bit なら 24bit のまま、32bit float なら float のまま出すので、ビット精度は元ファイルと完全に一致します。「分割したら微妙に音が変わった」が起きません。

再エンコード時: エンコーダを使い回す

ビットレートを指定した場合だけエンコードします。ここでもセグメントごとに AudioEncoder を作り直すと初期化コストが積み上がるため、同じ設定で書き出す間は1 つのセッションを使い回すようにしました。WebCodecs の AAC が使えない環境では ffmpeg.wasm にフォールバックします（初回のみ約 30MB の読み込み）。

5. 地味に効く: 同期ズレとの戦い

コピー経路を入れると、今度は波形と再生位置がずれる問題が出ます。AAC にはエンコーダ遅延（priming）、MP3 には Xing ヘッダフレームと LAME タグの encoder delay があり、デコード結果の先頭には実際の音声より前のサンプルが含まれます。

  • m4a: elst（edit list）の media_time を読み、そのサンプル数を先頭で捨てる
  • mp3: 先頭の Xing/Info フレーム数 + LAME タグの delay + デコーダ固有の遅延 529 サンプル

これを WebCodecs のデコード出力から差し引くことで、decodeAudioData で作った波形と一致するようになりました。高速化の話に見えて、実際はここが一番デバッグに時間を使いました。

6. 結果

3 分ステレオ (44.1kHz) を 10 分割したときの書き出し時間です。

条件 改善前 改善後
m4a → m4a（元のまま） 1445 ms 47 ms
mp3 → mp3（元のまま） 7061 ms 28 ms
m4a（192kbps 再エンコード） 1404 ms 1568 ms

30 分ステレオ (44.1kHz) を 10 分割したときの全体です。

工程 改善前 改善後
デコード 4243 ms 4544 ms
波形ピーク 438 ms 487 ms
書き出し 16863 ms 232 ms
合計 21544 ms 5263 ms

再エンコードの 1568ms は改善前よりわずかに遅くなっています。これはエンコーダをセッションで使い回す代わりに、キュー制御と AudioData の組み立てを丁寧にやるようになったためです。書き出し経路の 99% は「元のまま」なので、全体としてはこちらを優先しました。

長いファイルでの体感

30 分のファイルではデコードと波形計算が支配的になるため、合計は 21.5 秒 → 5.3 秒です。ただし既定の「元のまま」では PCM デコード自体が走らないので、実際に待つのは波形が出るまでの 0.36 秒だけになります。

7. 試して撤回した高速化

速くするつもりが遅くなった例も残しておきます。計測していなければ、どちらも「良かれと思って」入れてしまっていたはずです。

波形ピーク計算の Worker 化（撤回）

ピーク計算を Worker に移せばメインスレッドが空くと考えましたが、30 分の音源ではチャンネル配列のコピーが数百 MB になり、438ms → 1652ms と逆効果でした。コピーせずに済む「表示範囲だけ計算する」方式に変えたことで、結果的に Worker 化の目的（UI を止めない）も達成しています。

Worker 内での AudioDecoder デコード（撤回）

Worker には OfflineAudioContext が無いため decodeAudioData は使えません。そこで AudioDecoder で MP4 サンプルを直接デコードし、ピークだけ返す方式を試しました。メインスレッドのブロックは397ms → 43ms に減りますが、デコード自体が遅く、30 分で 487ms → 7283ms と大幅に悪化したため撤回しました。「UI が固まらない」と「速い」は別物で、今回は後者を優先しています。

8. まとめ

今回の高速化は、アルゴリズムを賢くしたというより「やらなくていいことを見つけた」だけです。

  • メタデータはコンテナから読めるので、PCM デコードを待たない
  • 波形は見えている範囲ぶんしか要らない
  • 同じ形式への分割は、エンコードし直す必要がない
  • 再生はブラウザのメディアスタックに任せれば、自前で PCM を持たなくていい

ブラウザ内で完結する音声処理は、一見「WebAssembly で頑張る」話に見えますが、実際にはコンテナ仕様を読んで、データを触らずに運ぶほうが桁違いに速いことが多いです。mp3 のフレーム長も mp4 のサンプルテーブルも、仕様書に書いてある通りに読めば十分でした。

Symple Audio Splitter はブラウザで今すぐ使えます。ファイルはアップロードされず、インストールすればオフラインでも動きます。

Symple Audio Splitter is a browser-only audio splitter for mp3 / m4a. This article covers its performance work: showing the UI from container metadata alone (0.08 s for a 30-minute m4a), generating waveform peaks only for the visible range with WebCodecs AudioDecoder, and eliminating re-encoding entirely for same-format exports.

For same-format output, the app copies encoded frames: AAC samples are indexed from stbl and re-muxed with mp4-muxer (1445 ms → 47 ms for 10 segments), MP3 frames are sliced at frame boundaries (7061 ms → 28 ms), and WAV PCM is copied bit-exactly. A 30-minute file's export dropped from 16.9 s to 0.23 s. Two attempted optimizations (worker-side peak computation and worker-side AudioDecoder decoding) were measured and reverted because both were slower in practice.
