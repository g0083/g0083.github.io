【開発記】書き出しの 16.9 秒が消えた話 ― 音声分割 PWA から再エンコードを外すまで 【DevLog】The 16.9 Seconds That Disappeared: Removing Re-Encoding from an Audio Splitter

2026.11.10 著者: g0083 (O-ya tech) 関連: Symple Audio Splitter

30 分の音源を 10 個に切るのに、21 秒待たされていました。

うち 16.9 秒は書き出しです。中身は AAC へのエンコードし直しでした。切れ目を決めるだけの操作に、毎回エンコードが挟まっていました。

その工程を丸ごと外したら、0.23 秒になりました。

外せることに気づくまでが長かったです。

波形上のダブルクリックで分割線を追加、ドラッグで移動できます。プレビュー再生は元ファイルをそのまま <audio> に渡しています。

測ったら、書き出しが 8 割だった

最初の実装は素直でした。読み込み時に全部 PCM にデコードし、波形ピークを全編ぶん計算し、書き出すたびに AAC か MP3 にエンコードし直していました。機能はすべて動いていました。ただ、遅かったです。

自分は体感で判断すると外すので、まず計測環境を作りました。bench/ に Chrome を DevTools Protocol で動かす仕組みを置いて、デコード、波形ピーク、書き出し、合計を分けて記録します。

node bench/make-fixtures.mjs          # テスト音源を生成 (ffmpeg が必要)
node bench/run.mjs --label before --format m4a --bitrate original --splits 9 --repeat 3

30 分ステレオ (44.1kHz) を 10 分割したときの初期実装はこうでした。

工程 時間 支配要因
デコード 4243 ms 全編 PCM 化
波形ピーク 438 ms 全編を走査
書き出し 16863 ms 10 セグメントを毎回 AAC エンコード
合計 21544 ms

書き出しが 78% です。ここを削るのが最短でした。

ただ表を見ていて、別のことも気になりました。デコードと波形ピークは「書き出しに必要だから」という理由で読み込み時に走らせていました。再エンコードしないなら、どちらも要りません。書き出しを速くする前に、書き出しを消せるという話です。

読み込みでは、まだデコードしない

長さもサンプルレートもチャンネル数も、PCM にしなくてもコンテナのメタデータから読めます。そこで decodeAudioData を待たず、ヘッダを数ミリ秒読んだだけで画面を出すようにしました。

形式 読む場所 取り出す値
m4a moov > trak > mdia > mdhd / stsd 長さ、タイムスケール、チャンネル数、サンプルレート
mp3 フレームヘッダの連鎖 フレーム数、サンプルレート、平均ビットレート、チャンネルモード
wav fmt / data チャンク フォーマットタグ、ビット深度、データ長

再生も AudioBuffer を使うのをやめ、<audio> に Blob URL を渡すだけにしました。ブラウザのメディアスタックが勝手にデコードしてくれるので、アプリ側で PCM を持つ必要がありません。30 分の m4a が0.08 秒で操作可能になります。以前はここで 8〜10 秒止まっていました。

PCM が要るのは、再エンコードするときだけ

既定の「元のまま」では loadPcm() は一度も呼ばれません。遅延評価の Promise にしてあるので、同じファイルに対してデコードが走るのは最初の 1 回だけです。

波形も、見えている範囲しか作らない

波形ピークは 1 ピクセルに 1 個あれば足ります。全体表示なら 1 個が数万サンプルを持ち、拡大すれば数百サンプルです。全編を同じ精度で計算する理由がありません。

表示範囲と解像度からピーク間隔を決めて（256〜65536 サンプル、2 の冪）、範囲の先頭フレームへシークしてデコードする形に変えました。ズームやパンで足りない範囲だけ追加で取りに行きます。

// src/workers/peaks.worker.ts (抜粋)
// 1 ピークが複数フレームにまたがる場合はフレームを間引く
const frameSamples = /* 1 フレームのサンプル数 */;
const step = Math.max(1, Math.floor(bucket / Math.max(1, frameSamples)));
// 間引き時は 1 フレームのピークを step フレーム分へ引き伸ばす
const spanSamples = step > 1 ? step * frameSamples : 0;

デコードは WebCodecs の AudioDecoder で、100ms ごとに range-partial を返しながら波形を左から埋めていきます。30 分の m4a で全体波形まで 0.36 秒。拡大したときは表示範囲の先頭からデコードし直すので、待ちはほぼ感じません。

拡大時のピークが decodeAudioData の結果と一致するかは確認しました。最大誤差 0.0007 です。

41MB はコピーしない

解析対象のバイト列はメインスレッドから送りません。File をそのまま Worker に渡して、Worker 側で arrayBuffer() させます。41MB を構造化クローンで複製すると、それだけでメインスレッドが数百ミリ秒止まるからです。

Worker も 2 つに分けました。波形用と RMS 用です。相乗りさせると、全編 RMS の計算中にズーム操作が待たされます。無音検出用の 10ms RMS は裏で作らせ、分割や書き出しを始めたら terminate() で切ります。

エンコードしなければ、書き出しは消える

同じ形式に戻すのに、なぜ毎回エンコードし直す必要があるのか？

要りません。音声データを作り直さず、切れ目をコピーするだけで成立します。

経路 方式
m4a → m4a（元のまま） AAC サンプルをコピーして mp4-muxer で再構成
mp3 → mp3（元のまま） フレーム境界でバイト列を切り出す
wav → wav（元のまま） PCM をフレーム境界でコピー（ビット深度も維持）
m4a（ビットレート指定） WebCodecs AAC + mp4-muxer
mp3（ビットレート指定） lamejs（Web Worker）

m4a: サンプル表を読んで、切り出す

mp4 の stbl にはサンプルごとの位置と長さが入っています。stco（チャンクオフセット）、stsc（チャンク内のサンプル数）、stsz（サンプルサイズ）を展開すれば、各 AAC サンプルのバイトオフセットが出ます。あとは範囲に入るサンプルを addAudioChunkRaw() で muxer に渡すだけです。

// src/audio/m4acopy.ts (抜粋)
const { from, to } = sampleRange(index, startSec, endSec);
const muxer = new Muxer({
  target,
  fastStart: 'in-memory',
  audio: { codec: 'aac', numberOfChannels: index.channels, sampleRate: index.sampleRate },
  firstTimestampBehavior: 'offset',
});

for (let i = from; i < to; i++) {
  const offset = index.offsets[i];
  const size = index.sizes[i];
  muxer.addAudioChunkRaw(bytes.subarray(offset, offset + size), 'key', timestamp, duration, meta);
  timestamp += duration;
}

エンコードが挟まらないので、10 分割でも 47ms です。30 分のファイルで 232ms。

分割点はサンプル境界に丸めて、隣り合う区間で同じ境界を共有させています。サンプルが重複することも、欠けることもありません。

mp3: フレームを数えて、バイト列を切る

mp3 はフレーム長がヘッダから決まります。全フレームのオフセットを一度インデックスにしておけば、指定時間にいちばん近いフレーム境界を探して subarray() するだけです。7061ms が 28ms になりました。

wav: PCM をそのまま運ぶ

wav は blockAlign の倍数で切って、44 バイトのヘッダを付け直すだけです。元が 24bit なら 24bit のまま、32bit float なら float のまま出します。ビット精度は元ファイルと完全に一致します。

「分割したら微妙に音が変わった」が起きないのは、地味ですが効いていると思います。

どうしても再エンコードするとき

ビットレートを指定した場合だけエンコードします。ここでもセグメントごとに AudioEncoder を作り直すと初期化コストが積み上がるので、同じ設定で書き出す間は 1 つのセッションを使い回しました。WebCodecs の AAC が使えない環境向けに ffmpeg.wasm のフォールバックも残しています。初回だけ約 30MB 読み込みます。

速くしたら、ズレた

コピー経路を入れた直後、波形と再生位置がずれました。

AAC にはエンコーダ遅延（priming）があります。MP3 には Xing ヘッダフレームと LAME タグの encoder delay があり、デコード結果の先頭には実際の音声より前のサンプルが入ります。

  • m4a: elst（edit list）の media_time を読み、そのサンプル数を先頭で捨てる
  • mp3: 先頭の Xing/Info フレーム数 + LAME タグの delay + デコーダ固有の遅延 529 サンプル

これを WebCodecs のデコード出力から差し引くと、decodeAudioData で作った波形と一致しました。

高速化の記事なのに、いちばんデバッグに時間を使ったのはここです。

結果

3 分ステレオ (44.1kHz) を 10 分割したときの書き出し時間です。中央値、3 回の計測。

経路 改善前 改善後
m4a → m4a（元のまま） 1445 ms 47 ms
mp3 → mp3（元のまま） 7061 ms 28 ms
wav → wav（元のまま） — 67 ms
m4a（192kbps 再エンコード） 1404 ms 1568 ms
mp3（192kbps 再エンコード） — 10653 ms

wav だけ 24bit PCM（47.6MB）で測っています。改善前の値がないのは、当時 wav のコピー経路が存在せず、比較対象が別物になるためです。

30 分ステレオを 10 分割したときの全体はこうです。

工程 改善前 改善後
デコード 4243 ms 4544 ms
波形ピーク 438 ms 487 ms
書き出し 16863 ms 232 ms
合計 21544 ms 5263 ms

再エンコードの 1568ms は、改善前の 1404ms より少し遅くなりました。エンコーダをセッションで使い回す代わりに、キュー制御と AudioData の組み立てを丁寧にやるようになったためです。

書き出しの既定は「元のまま」なので、自分はこちらを優先しました。ただ、この判断は利用頻度の推測に依存しています。ビットレート指定が主流の使い方なら、逆の選択になります。

長いファイルでの体感

30 分のファイルでは、合計は 21.5 秒 → 5.3 秒です。ただ、既定の「元のまま」では PCM デコード自体が走りません。この 5.3 秒を待つことは、実際にはありません。待つのは波形が出るまでだけです。

速くしたつもりが、遅くなった案

撤回したものも残しておきます。計測していなければ、どちらも「良かれと思って」入れていたはずです。

ピーク計算だけ Worker に移す

メインスレッドが空くと考えました。30 分の音源ではチャンネル配列のコピーが数百 MB になり、438ms が 1652ms に増えました。

ただ、この案が解こうとしていた問題（UI を止めない）は、あとから「表示範囲だけ計算する」方式に変えたときに一緒に解決しています。速さと応答性は別の軸なので、片方だけ追うと判断を誤ります。

Worker の中で AudioDecoder を使う

Worker には OfflineAudioContext が無いので decodeAudioData は使えません。そこで AudioDecoder で MP4 サンプルを直接デコードし、ピークだけ返す方式を試しました。

メインスレッドのブロックは 397ms から 43ms に減ります。しかしデコード自体が遅く、30 分で 487ms が 7283ms になりました。15 倍遅いので、さすがに採れません。

「UI が固まらない」と「速い」は別物です。今回は後者を取りました。

おわり

今回やったのは、アルゴリズムを賢くすることではありませんでした。やらなくていい処理を探して、外しただけです。

メタデータはコンテナから読めます。波形は見えている範囲ぶんしか要りません。同じ形式への分割はエンコードし直す必要がありません。再生はブラウザのメディアスタックに任せれば、自前で PCM を持つ必要もありません。

ブラウザ内で完結する音声処理は、WebAssembly で気合を入れる話に見えます。自分も最初はそう思っていました。実際には、コンテナ仕様を読んでデータを触らずに運ぶほうが桁違いに速いことが多いです。mp3 のフレーム長も mp4 のサンプルテーブルも、仕様書に書いてある通りに読めば足りました。

冒頭の 21 秒に戻ると、あの時間の大半は「切り分ける」仕事ではなく「作り直す」仕事でした。分割という操作に、変換が混ざっていたわけです。

手元のツールでも、そうなっている箇所は一度探してみると面白いと思います。

Symple Audio Splitter is a browser-only audio splitter for mp3 / m4a. This article covers its performance work: showing the UI from container metadata alone (0.08 s for a 30-minute m4a), generating waveform peaks only for the visible range with WebCodecs AudioDecoder, and eliminating re-encoding entirely for same-format exports.

For same-format output, the app copies encoded frames: AAC samples are indexed from stbl and re-muxed with mp4-muxer (1445 ms → 47 ms for 10 segments), MP3 frames are sliced at frame boundaries (7061 ms → 28 ms), and WAV PCM is copied bit-exactly. A 30-minute file's export dropped from 16.9 s to 0.23 s. Two attempted optimizations (worker-side peak computation and worker-side AudioDecoder decoding) were measured and reverted because both were slower in practice.
