日常会話に強い極小IMEモデル「ZeroCon Nano v4.1」と共有エンジンへのnam数値マスク統合

2026.11.15 著者: g0083 (O-ya tech) 対象バージョン: ZeroConvert-IME v0.7.0

極小モデルの変換精度がカタログ数値だけ良くなっても、普段のチャットや数値混じりの入力で崩れては意味がない。ZeroConvert-IME v0.7.0では、標準モデルを6層・約26.7MパラメータのZeroCon Model Nano v4.1へ刷新し、あわせてベンチマーク専用だった数値マスク機構をWindowsとAndroidの実変換エンジンへ組み込んだ。

サイズとアーキテクチャの前提はNano v4から変えていない。既定のIQ4_emb8版は18.7 MiB、Q8版は27.7 MiBに収まる。追加したのは、日常的な短文・口語表現・補助動詞のひらがな保持を扱う学習カリキュラムと、実IMEでそのまま数字の誤変換を防ぐ共有パイプラインだ。

1. なぜ従来の長いベンチマークだけでは足りなかったのか

これまでの開発評価では、新聞や解説文のように長い複文でモデル単体の正答率を見てきた。だが実際のZeroConvert-IMEには自動確定があり、画面上に長大な未確定文が溜まり切る前に先頭部分が確定する。入力される単位が短いほど、モデルの弱点は違う場所に現れる。

具体的に気になったのは日常チャットと口語の崩れ、それに過剰漢字だった。たとえば食べているのに漢字で「食べて行く」と出たり、「ありがとうございます」が「有難う御座います」寄りに引っ張られたりする挙動は、4bit量子化を施した軽量モデルで特に目立ちやすい。

実利用に近い条件で弱点を測るため、160問のIME実経路想定セットと100問の日常口語・過剰漢字セットを新しく設計した。既存の230問セットおよび高難度250問セットと合わせた計740問で、学習段階のr1からr2、v4.1となるcap-nam-r3までを順に検証している。

2. v4.1で入った学習改善とデータリーク隔離

学習基盤にはこれまでと同様、rank-64のDoRA、Target-Corrected二重アンカー蒸留、自己コピーと早すぎるEOSの抑止を使っている。v4系の基礎能力強化ではこれに加え、正解トークンと次点候補のロジット差を保つquant_marginと文脈引きずりを抑えるprior_copy_marginを導入した。r2からr3にかけては、口語縮約、ネットスラング、補助動詞のひらがな維持、過剰漢字抑止を重点的に補強している。

学習時に統合されたLoRA/DoRA重みはベースモデルへマージ済みのため、推論時に追加レイヤーは走らない。教師モデルには同じカリキュラムで育てた12層・90.5MパラメータのStandard v4.1を使った。

学習と評価のデータリーク検証

nano-v4-cap-nam-r3-lora/dataset-provenance.json の記録では、source-components-nfkc-kana-v1 ポリシーのもと学習1,274件・検証121件を構築している。主要7種の評価データセットとの間で、train_evaluation_shared_keys、validation_evaluation_shared_keys、evaluation_derived_rows、train_validation_shared_groups はいずれも0件だった。

3. 計740問での精度推移：口語100問で87%から97%へ

r2からr3（Nano v4.1）への更新で最も大きく伸びたのが口語・日常チャット領域だ。CPU上での単体モデル比較では、Nano IQ4_emb8が87/100（87.0%）から97/100（97.0%）へ、Nano Q8が92/100（92.0%）から98/100（98.0%）へ改善した。補助動詞やネットスラング、口語縮約はいずれも20/20に達している。

Windowsの共有変換パイプライン上でNano v4.1 IQ4を使った548問のタイポ補正評価でも、登録済みタイポ群は0から90/92がTop-1に浮上し、Top-5には92/92すべてが入った。正常入力コントロール群156問に対する誤補正は0件だった。なお、これらは固定データセットによるモデル・パイプライン測定値であり、未知の実打鍵すべてに対する保証値ではない。

4. ベンチマーク専用の仕組みを実IMEの共有エンジンへ移植する

精度検証の過程では、連続した数字列を一時的に nam というプレースホルダへ置き換えてモデルへ渡し、返ってきた出力文字列へ元の数字列を書き戻す前処理を使っていた。モデルの語彙や学習データ内で桁数違いや全半角の揺れに振り回されず、文脈上の助数詞や単位だけを正しく変換させる狙いだ。

ただし、この変換がベンチマークスクリプトの中だけに留まっていては、実際のIMEユーザーが数字を入力したときに同じ恩恵を受けられない。v0.7.0では設計を見直し、通常のライブ変換、タイポ補正、先読みアシストのすべてで同じ nam マスクと復元を通すように統一した。

プラットフォーム / 層 組み込み先モジュール 担う処理
Windows Swift変換器 ZenzDigitMasking (converter_patch.py) 通常変換の左文脈・読み仮名マスクとデコードバイト列上の復元
Windows Rustサーバー corrector::mask_digits_with_nam / restore_nam_digits タイポ補正、Keyboard Hybrid修復文脈、先読み補完のマスクと復元

なぜ2パス復元で英単語を守れるのか

nam 復元で一番気をつけなければならないのが英単語との衝突だ。たとえば入力文や変換候補に name、naming、dynamic、username が含まれていると、単純な前方一致置換では 10e や dy10ic のように英単語を壊してしまう。

そこで共有実装では、どの言語層でも同じ2パス方式を採用した。まず第1パスでは、直後に小文字アルファベットが続く nam を英単語とみなしてスキップする。ただし x だけは除外しており、10x のように倍率記号と連結したケースは第1パスでそのまま数字に戻る。

第1パスを終えてもまだ元の数字列が余っている場合だけ、第2パスが走る。第2パスでも直前が小文字のケース（dynamic）、直後が e のケース（name / username）、後ろに単独の ing が続くケース（naming）は英単語として保護しつつ、日本語の助数詞ローマ字や複合語に吸収された残りスロットだけを補完する仕組みにした。Swift変換器では、推論途中で na や n までしか出力されずに打ち切られた末尾フラグメントへの復元も備えている。

例: 「SELECT name FROM customers」と「１００えんのあめ」が混在しても
1) 入力マスク: 「１００えんのあめ」 → 「namえんのあめ」(digits=["100"])
2) 英単語混在テスト: restore_nam_digits("SELECT nameです dynamic", ["10"])
   → 末尾e・直前小文字判定により "SELECT nameです dynamic" のまま破壊されない
3) 倍率記号混在テスト: restore_nam_digits("Wi-Fi namEとBluetooth nam.nam", ["6", "5", "4"])
   → 各スロットへ左から順に還元され "Wi-Fi 6EとBluetooth 5.4" を復元

学習データの更新と共有エンジンの前処理が噛み合ったことで、740問ベンチマークの数値例はすべて全問一致の100%で通るようになった。同じバイナリと設定をWindowsインストーラーおよびAndroid APKとしてv0.7.0に収録している。
