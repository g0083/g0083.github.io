ZeroConvert-IMEの推論高速化――llama.cppグラフ初期化削減、Swiftコンテキスト再利用、Android KVプレフィックス共有

2026.11.15 著者: g0083 (O-ya tech) 対象バージョン: ZeroConvert-IME v0.7.0

日本語IMEの変換推論は、数GB級のLLMで長文を生成するときとはボトルネックの場所がまるで違う。入力される読みは十数トークン程度と短く、1回ごとの行列積そのものはごく軽量だ。むしろコンテキストの再確保、不要なカーネル探索、全語彙LogSumExp、スレッドディスパッチといった周辺オーバーヘッドが打鍵レスポンスを左右する。

ZeroConvert-IME v0.7.0にかけた一連の改修では、モデル構造を6層のNano系へ軽くしただけでなく、llama.cpp本体のコンテキスト初期化、Windows側のSwift変換器、Android JNIのKVキャッシュ管理、そして常駐プロセス構成まで手を入れた。

1. llama.cpp側で使われない融合グラフ探索を止める

ZeroCon系の日本語変換モデルはGPT-2ベースの設計をとる。ところが現代のllama.cppは多様な大型モデルに対応するため、コンテキスト予約時にGDN、Lightning Indexer、DeepSeek V4向けHyper-Connectionsなどの融合演算グラフが使えるかを毎回プローブする既定値を持っていた。

patches/llama.cpp/zerocon-compat-b12125.patch の src/llama-context.cpp パッチでは、アーキテクチャが LLM_ARCH_GPT2 である場合に限り、fused_gdn_ar、fused_gdn_ch、fused_lid、fused_dsv4_hc_pre、fused_dsv4_hc_comb、fused_dsv4_hc_post、auto_fhc の各フラグを明示的に無効化した。あわせてコンテキストサイズやバッチパラメータ、Flash Attention、パフォーマンス集計停止を見直している。

if (model.arch == LLM_ARCH_GPT2) {
    cparams.fused_gdn_ar       = false;
    cparams.fused_gdn_ch       = false;
    cparams.fused_lid          = false;
    cparams.fused_dsv4_hc_pre  = false;
    cparams.fused_dsv4_hc_comb = false;
    cparams.fused_dsv4_hc_post = false;
    cparams.auto_fhc           = false;
}

同一マシン・同一モデル zerocon-nano-v4.1-iq4nl-emb8.gguf を使ったCPU条件の横並び計測では、このランタイムパッチと llama-server 設定最適化により、初回コールドプロンプトの平均遅延が23.13 msから19.60 ms、中央値が27.83 msから20.96 msへ短縮した。

2. Swift変換器でのコンテキスト再利用とシングルパス評価

Windows側の中核を担うSwift製の変換器パッケージ AzooKeyKanaKanjiConverter は、これまでリセットのたびに llama_context を破棄して作り直す経路が残っていた。これを ZenzContext.resetContext() で llama_memory_clear のみを呼び出し、確保済みのコンテキストと計算グラフをそのまま再利用する形へ改めている。

初期化設定自体もIMEの短いコンテキストに合わせて調整した。コンテキスト長 n_ctx=1024、統一KVバッファ n_seq_max=2・kv_unified=true、n_batch=1024、n_ubatch=512、最大出力 n_outputs_max=256、LLAMA_FLASH_ATTN_TYPE_ENABLED、no_perf=true とし、スレッド数も1トークン生成用の decodeThreads とまとめて評価する batchThreads を分けて動的に切り替える。

候補スコアを評価する ZenzCandidateEvaluator では、複数候補の完全な確率分布を要しない経路向けに !requestRichCandidates 時の生ロジット一巡argmax高速パスを入れた。全語彙の stabilizedLogSumExp を計算するタイミングも早期終了判定の後へ遅らせている。

3. Android JNIの共通プレフィックスKVキャッシュ共有

スマートフォンの入力体験に直結するのがAndroid JNI層 zenz_jni.cpp と assist_jni.cpp のKVキャッシュ管理だ。ライブ変換では1打鍵ごとに末尾の1文字だけが増えたプロンプトが繰り返し飛んでくる。先頭から左文脈を含めて毎回ゼロから再評価していては、限られたモバイルCPU時間とバッテリーを無駄に消費する。

新しい実装では前回のトークン列 g_cached_tokens を保持し、今回のトークン列との最長共通プレフィックス長 common_len を計算する。一致した箇所まではKVキャッシュに計算済み状態を残したまま、分岐した末尾以降だけを llama_memory_seq_rm(mem, 0, common_len, -1) で破棄し、差分トークン prompt_delta のみを評価する。

もう一つ効いたのがスレッド数の切り替えだ。差分 prompt_delta が4トークン以下の細かな増分更新では g_batch_threads を起こさず g_decode_threads のまま回し、スレッド起床のオーバーヘッドを抑えた。キャッシュ状態の整合チェックとして llama_memory_seq_pos_max(mem, 0) == common_len - 1 を検証し、食い違いを検知した場合は即座にクリアへフォールバックする安全策も入れている。

4. モデル統合・CUDA廃止によるフットプリント削減とパイプライン実測

これまでWindows版のタイポ補正は独立サーバーとしてポート18090に常駐し、さらにGPUオフロード用にCUDAランタイムと設定コードを抱えていた。v0.2.3以降の一連の整理を経て、v0.7.0ではスタンドアロンのCorrector常駐プロセスおよびCUDA固有コード（cuda_backend.rs）を完全に廃止した。現在は通常のメインモデルプロセス1本で、通常変換・Keyboard Hybridタイポ補正リランキング・先読みアシストを一気通貫で処理する。

Windowsの共有変換エンジンを用いた548問のタイポ補正ベンチマークでは、Nano v4.1 IQ4_emb8構成で通常変換時の中央値49.24 msに対し、タイポ補正を有効にした場合でも中央値52.87 msに収まった。同一ケースごとのペア差分中央値はわずか +1.14 ms にとどまる。標準モデルにNano v4.1 IQ4を選ぶと、12層のStandard v4.1 Q8と比べてCPU単体平均遅延で約3.3倍から4.1倍速く、ピークRSSメモリも約64%から65%抑えられる。

上記の遅延およびRSS数値はいずれも開発PC上のCPU条件（-ngl 0）で測定したモデル推論およびSwift評価パイプラインの記録であり、各ユーザーのOS環境やアプリ側のUI再描画時間すべてを表すものではない。

極小モデルと推論パイプラインの軽量化を組み合わせた結果、メモリ常駐量を大きく減らしながら日常入力で違和感のない応答速度を維持できる土台が整った。最新の改善を取り込んだバイナリはv0.7.0で配布している。
