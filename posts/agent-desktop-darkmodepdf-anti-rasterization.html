Architecture / Rust & PDF

【考察】脱ピクセルの「agent-desktop」と、PDFを画像化せず中身を書き換える「DarkModePDF」――構造化データを直接叩く設計の共通点

投稿日: 2026年11月23日 筆者: O-ya tech (g0083) 関連: DarkModePDF / Markdown TeX Viewer / agent-desktop
Related Project / 関連プロジェクト DarkModePDF & Markdown TeX Viewer
PDF内部ストリームを直接変換するDarkModePDF（Android / Web PWA）と、Typst WASMでベクターPDFを出力するMarkdownエディタ
DarkModePDF ↗ TeX Viewer ↗

コンピュータを操作するAIエージェントの実装は、長らく画面のスクリーンショットを撮ってVisionモデルに渡し、ボタンのピクセル座標を当てさせるやり方が主流だった。ところが解像度やDPIの違いで座標がずれ、毎ターン画像トークンを消費するため遅くて高い。

この非効率を真正面からひっくり返して2026年11月のGitHub Trendingで注目を集めているのが、Vercel Labsが公開したRust製CLIおよびCライブラリ vercel-labs/agent-desktop だ。内部にLLMを持たず、macOS AX API、Windows UI Automation、Linux AT-SPIといったOS標準のアクセシビリティツリーを直接叩いて構造化JSONを返す。

実装の考え方を眺めていて既視感を覚えた。筆者が作ってきた DarkModePDF や Markdown TeX Viewer でも、最初にぶつかった壁と突破口はまったく同じだったからだ。どちらも「見た目（ピクセル）に一度潰してから処理する」安易なルートを捨て、裏側の構造化表現を直接扱うことで初めて実用になる。

1. agent-desktopが「スクリーンショット」を捨てた理由

agent-desktop のループは極めてドライで実務的だ。AIエージェント（Claude Codeなど）はシェル経由または組み込みのMCPサーバー（agent-desktop mcp）経由で snapshot を叩き、操作可能なUI要素に割り当てられた参照IDを受け取る。 

# 1. 画面を撮らずにOSのアクセシビリティツリーを取得
agent-desktop snapshot --app "Finder" -i

# 2. スナップショットID付きの安定したref（例: @s8f3k2p9:e8）に対して操作を実行
agent-desktop click @s8f3k2p9:e8
agent-desktop type @s8f3k2p9:e12 "report.pdf"

ここで特にうまいのが、参照IDが特定のスナップショットIDに紐づいている点だ。操作前にUIが変化して要素が消えたり位置が変わったりしていた場合、agent-desktop は見当違いの座標をクリックする代わりに STALE_REF エラーを返して安全に止まる。さらに既定でヘッドレス動作（アクセシビリティAPI経由のバックグラウンド操作）をとるため、物理マウスカーソルやウィンドウフォーカスを奪わない。

構造を直接読むと何が消えるか

画面をPNG化してからOCRや座標推定を走らせる方式では、フォント差、スケーリング倍率、重なり順の誤認といったノイズが避けられない。OS自身が保持している意味ツリーをそのまま読めば、ロール名・状態・テキスト・バウンディングボックスをゼロ誤差で取り出せる。

2. PDFでもまったく同じ罠がある――画像化方式の破綻

実はPDFの世界でも、これと瓜二つの失敗パターンが繰り返されてきた。かつて DarkModePDFの開発記 に書いた通り、白背景のPDFをダークモード変換する一番簡単な実装は「各ページをPNGとしてレンダリングし、Canvasで色反転してPDFへ貼り直す」ことである。

だが一度ピクセルへラスタライズした瞬間、ドキュメントが本来持っていた構造情報はすべて吹き飛ぶ。

  • ベクターの文字や罫線がビットマップに潰れ、拡大すると輪郭がぼやける。
  • テキストレイヤーが消滅するため、文字列の選択・検索・コピーができなくなる。
  • 1MBだった論文PDFが数十MBに膨れ上がり、モバイル端末のメモリを圧迫する。
  • ページ内の写真やグラフまでネガフィルムのように色反転してホラー画像と化す。

Markdown TeX Viewer のPDF書き出しでも同じ問題に直面した。html2canvas でDOMを画像に焼いてPDF化する一般的なWeb実装だと、数式が荒れて論文用途に耐えない。そこで入力プレビューはKaTeXとMarkdown-itで60fpsのDOM描画を行いつつ、書き出し時はWeb Worker上の Typst WebAssembly にASTから変換した組版コードを渡し、完全なベクターPDFバイナリを生成する道を選んだ。

3. 「中身を直接書き換える」泥臭さと安全装置の共通点

構造化表現を直接触る設計は美しく聞こえるが、実装の現場では仕様の隅を突く泥臭い対処が欠かせない。DarkModePDFでは、そもそも多くのPDF仕様上に「白い背景オブジェクト」が存在せず紙の白が透けているだけだと知り、コンテンツストリームの先頭へ黒い塗りつぶし矩形コマンド q 0 0 0 rg ... re f Q を割り込ませる必要があった。

さらに文字や罫線の色オペレータ（rg / RG / g / G / k / K）だけを解析して反転し、埋め込み画像オブジェクト（XObject /Subtype /Image）はスキップして写真を保護する。数百ページのPDFでモバイルOSのOOMを食らわないよう、1ページずつ逐次ストリーム処理とバッファ解放を回す泥臭さもセットだった。

一方で agent-desktop に目を戻すと、スナップショットID付きの参照に加えて、要素の多い重量級アプリでツリー全ダンプが重くなりすぎるのを防ぐ --skeleton や --root による段階的ドリルダウンを備えている。構造化データであっても無制限に展開すればメモリとトークンを食い潰すため、「必要な部分だけを境界切って読む」設計が効いている。

状態ズレを「誤爆させず検知する」思想

DarkModePDFが「画像XObjectに触れない」「1ページずつ破棄して次へ進む」境界を引くのと同じように、agent-desktop は STALE_REF で「古い仮定のまま次工程へ進まない」保証を入れている。筆者がZeroConvert-IMEのAndroid層でキャッシュ共有を実装した際も、整合チェックが外れたら即座にキャッシュクリアへフォールバックさせました。構造を直接操作する実装ほど、前提が崩れた瞬間に止まる安全装置が命綱になる。

4. 2026年11月のツール群に広がる「中間ラッパー排除」の流れ

この傾向はデスクトップ操作に限らない。はてなブックマークのITカテゴリで話題になった次世代メールプロトコル「JMAP」は、レガシーなIMAPのテキストベースのやり取りやポーリングの煩雑さを捨て、HTTPとJSONの構造化同期へ振り切ることでWebメール開発を単純化した。Zenn周辺で議論が活発なClaude Codeの拡張機構 mods やDocker Sandboxesによる隔離、OpenSpec v2.0のスキル一元化（.agents/skills/）も、曖昧な自然言語プロンプトや場当たり的な画面操作に頼らず、型や境界・仕様ファイルという構造側へ責務を寄せる動きと地続きに見える。

個人開発のツールでも、大企業の基盤でも、結局強いのは「一度人間向けの見た目やテキストに潰したものをAIや別プロセスに再解釈させる」のではなく、プログラムが本来持っている構造・命令ストリーム・ツリーをそのまま触れるレイヤーに立つことだ。

おわりに

vercel-labs/agent-desktop が見せた「スクリーンショットを捨ててOSのアクセシビリティツリーを直接読む」アプローチは、DarkModePDFでPDFの描画命令ストリームを書き換え、Markdown TeX ViewerでTypst WebAssemblyから直接ベクターPDFを吐き出したときの感覚と重なる。ピクセルに落とすのは最後の出力だけにして、途中の変換と操作は構造のまま回す。この原則を押さえておくだけで、ローカルツールもAIエージェントも驚くほど軽く壊れにくくなる。
