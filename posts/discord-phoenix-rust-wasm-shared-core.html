【考察】Discord「Project Phoenix」のRust×WASM共有コアと、脱Electron時代に個人開発アプリが採った同じ生存戦略

投稿日: 2026年11月20日 筆者: O-ya tech (g0083) 関連: Markdown TeX Viewer / ZeroConvert-IME / Symple Audio Splitter
Related Project / 関連プロジェクト Markdown TeX Viewer
Typst WebAssembly内蔵・ブラウザ完結型 Markdown & TeX エディタ（Web PWA / Android）
トップで見る ↗ GitHub

2026年11月、開発者コミュニティで大きな話題を集めたのが、Discord共同創業者兼CTOのStanislav Vishnevskiy氏がプレビュー公開した次世代クライアント刷新計画「Project Phoenix」である。

デスクトップ版の Electron（Chromium + Node.js） とモバイル版の React Native を両方捨て、アプリケーションの中核ロジックを 単一のRustコア へ統合する。デスクトップUIにはZedエディタチーム発のGPUアクセラレーション対応Rust製フレームワーク GPUI を採用し、ブラウザ版には同じRustコアを WebAssembly（WASM） へコンパイルして供給する構成だ。

Windows 11上の初期プレビューでは、複数アカウントを同時に稼働させた状態でもメモリ消費量が 約290MB に収まったことが示され、アイドル時でも1〜2GB、ヘビーユースでは4GB超に達していた従来のElectron版からの劇的な軽量化が注目を集めている。

このニュースを見て強く共感したのは、筆者自身が個人開発でメンテナンスしている Markdown TeX Viewer（Typst WASM）や ZeroConvert-IME（18.7 MiB極小モデル＋共有ネイティブエンジン）、Symple Audio Splitter（サーバーレス音声分割PWA）もまた、規模こそ違えど「重い汎用ラッパーを捨て、コアをRust/ネイティブとWASMに分離する」というまったく同じ設計思想に辿り着いていたからである。

1. 「UIまで1つのWeb技術で統一する」時代の限界

これまでのクロスプラットフォーム開発では、「デスクトップもWebもChromium（Electron）＋JavaScriptで統一すれば1コードベースで済む」という考え方が主流だった。しかし2026年現在、ローカルAI（SLM）やリアルタイム音声・メディア処理がクライアント側へ降りてきたことで、その前提が崩れている。

  • メモリ予算の奪い合い： アプリのUI枠だけで1GB〜2GBのRAMを占有してしまうと、ユーザーの手元でローカルLLMや開発ツールを同時稼働させる余地がなくなる。
  • 起動レイテンシの壁： V8とChromiumプロセス群を立ち上げる数秒の待ち時間は、毎日何度も開くエディタや常駐コミュニケーションツールでは明確なストレスになる。
  • Webの進化： ブラウザ自身がPWA・Web Worker・File System Access API・WebAssemblyを標準装備したことで、「ローカルファイルを触りたいだけならElectronを配る必要すらない」領域が広がった。
💡 Project Phoenixが示した解：共有すべきは「UI」ではなく「Core」

Discordは「すべての画面を同じHTML/CSSで描く」ことを諦める代わりに、状態管理・通信・ビジネスロジックなどのCore層だけをRustで統一し、出力先に応じて GPUI（デスクトップ）、ネイティブUI（モバイル）、HTML＋WebAssembly（ブラウザ）を使い分ける判断を下した。

2. 個人開発3プロジェクトで実践した「脱重量ランタイム」の実測値

大規模プロダクトだけでなく、個人開発レベルでも「Electronや重いバックエンドを挟まない設計」にすると、ユーザー体験と開発コストのバランスがどう変わるか。これまでに公開・運用してきた3つのアプリの実測データと構造を整理してみる。

特に Markdown TeX Viewer では、Rustで書かれた組版エンジン Typst を WebAssembly 化してブラウザの Web Worker に閉じ込めたことが決定打になった。もしこれを Electron で配布していたら、毎回アップデートごとに数百MBのバイナリを配布する羽目になるが、PWA＋Typst Wasmならブラウザだけでオフライン動作し、ローカルの .md ファイルも直接上書きできる。

また ZeroConvert-IME でも、WindowsとAndroidのUI・OSフック層（TSF / InputMethodService）はそれぞれのネイティブ言語で薄く書きつつ、数値表記の誤変換を減らす仕組みといった変換ロジックを共有エンジン側に寄せることで、推論メモリ約35MB・コールド中央値 20.96ms という常駐可能なフットプリントを維持できている。

3. ただし魔法ではない――「速く軽くする」と代わりに何が重くなるのか？

ちょうど本日（2026年11月20日）のZennでも『検索を速くすると、代わりに何が重くなるのか』といった設計トレードオフの記事が注目を集めていたが、これはクライアントアーキテクチャでもまったく同じである。Electronを捨てて「Rust/ネイティブコア＋WASM」に移行すると、RAMと起動時間は劇的に軽くなる一方で、確実に重くなる場所（コストの移動先）が存在する。

トレードオフ ①：DOMとWASMの境界（メモリコピーと初期化）

WASMは高速だが、ブラウザのDOMを直接触る処理や、巨大なアセット（フォントや辞書、モデル重み）をJS側からWASM線形メモリへ渡す境界には必ずコストが発生する。 

// Markdown TeX Viewer における責務分離の例
// 1. 入力中の60fpsプレビューはメインスレッドのDOM (Markdown-it + KaTeX) で完結
//    → 1打鍵ごとにWASM境界を跨ぐとマーシャリングと再レイアウトで詰まる
// 2. PDF書き出し時のみ Web Worker 上の Typst Wasm へAST/テキストを渡す
const pdfBytes = await typstWorker.compile({
    mainFile: typstDoc,
    fonts: cachedFontBuffers // 初回のみ転送しWorker側で保持
});

Discord Phoenixがブラウザ版で「UI描画は標準HTMLのまま残し、アプリケーションロジックだけをWASMに載せる」構成を選んだのも、まさにDOM境界を跨ぐオーバーヘッドを避けつつロジック共有の恩恵だけを取るためである。

トレードオフ ②：UI層のプラットフォーム固有実装コスト

Electronなら1つのCSSとHTMLでWindows・macOS・Linux・Webがすべて同じ見た目になる。しかしコアだけをRust/C++で共有する戦略を採ると、デスクトップはGPUI、モバイルはSwift/Kotlin、WebはHTML/CSSというようにUI層の保守コストはプラットフォーム数に比例して重くなる。

実際、ZeroConvert-IMEでも変換コアは共有できているが、WindowsのTSF候補ウィンドウ制御とAndroidのソフトウェアキーボード（IMEサービス＋片手操作レイアウト）は完全に別実装として維持する必要がある。

トレードオフ ③：ビルドパイプラインとデバッグ体験

ブラウザやNode.jsだけで完結していた開発体験と比べ、wasm-bindgen・JNI・NDK・GPUIといったマルチターゲットのビルド環境は複雑になりやすい。実際、先日の llama.cpp v1.0.0記事 でも触れたとおり、C/C++/Rustライブラリを複数OSへ組み込む現場では、ABI安定性とビルド手順の自動化が開発速度を左右する。

⚠️ 個人開発での見極めライン

「画面が100個ある業務管理画面」ならWeb/Electronのまま生産性を優先した方がよい。逆に、「常駐するツール（チャット・IME）」「重い計算やバイナリ処理を伴うツール（組版PDF・音声分割・ローカルSLM）」では、UIをブラウザ/ネイティブに委ねてCoreをRust/WASM/C++に切る投資が確実に回収できる。

4. まとめ：小さいチーム・個人開発ほど「Core共有＋薄いUI」が効く

DiscordのProject Phoenixは、巨大サービスであっても「ユーザーのメモリを1GB以上奪う汎用ラッパー」がもはや許容されなくなってきた象徴的な転換点だ。

そして面白いことに、個人開発の現場ではすでに同じ構造が強力な武器になっている。重いサーバーも巨大なデスクトップラッパーも持たず、コア計算はRust（WASM）や極小ネイティブエンジンに寄せ、配信はブラウザPWAやOS標準UIへ載せる。今回のPhoenixの続報やGPUIエコシステムの成熟は、こうした軽量クライアント設計がこれからさらに当たり前になっていくことを裏付けている。
